# WorkFit 5주차 AI 피드백 개인 활동 보고서

## 1. 담당자 및 담당 기능

- 담당자: 전세현입니다.
- 담당 기능: 실습 답안에 대한 AI 피드백의 서버 정답 조회, 평가 기준 구성, 응답 검증 및 독립 데모를 담당했습니다.
- 작성일: 2026년 10월 31일 기준으로 작성했습니다.

팀원 담당 DB 스키마·관리자 API·프론트엔드는 이번 마무리 작업에서 수정하지 않았습니다.
새로 작성한 문서와 최종 표기 수정은 `backend/ai` 안에서 진행했습니다.

## 2. 5주차 개발 목표

4주차의 AI 호출·Mock 시연 기능에서 발전하여 서버가 신뢰할 수 있는 평가 근거를 제공하도록 개선하고자 했습니다.
학습자가 임의 정답이나 평가 기준을 보내 점수를 조작하지 못하도록 요청 경계를 분리하고자 했습니다.
정답·부분 정답·오답·평가 보류를 일관되게 처리하고, 실제로 검증하지 못한 연동을 완료로 표시하지 않도록 했습니다.
팀원에게 전달할 API 안내와 재현 가능한 테스트 절차를 문서화하고자 했습니다.

## 3. 이번 주 구현한 기능

1. 실제 평가 요청을 `practice_id`, `learner_answer`, 선택적 `answer_type` 중심으로 분리했습니다.
2. 기존 `practices`와 연결된 콘텐츠·과정 정보를 읽기 전용으로 조회하도록 구현했습니다.
3. 서버에 저장된 정답과 기준으로 내부 평가 요청을 구성하도록 구현했습니다.
4. 필수 기준의 누락·충돌과 지원 범위 밖의 답안은 `needs_review`로 보류하도록 구현했습니다.
5. 제한된 수식 구조 루브릭 및 숫자·텍스트 결과 비교를 구현했습니다.
6. 제공자 점수·판정·근거를 서버 계산과 대조하는 검증을 구현했습니다.
7. SUMIF·SUMIFS·IF의 평가 세트와 추가 오류·조작 방지 테스트를 작성했습니다.
8. 기존 Mock을 유지하면서 DB 없이 사용할 수 있는 독립 루브릭 데모를 추가했습니다.
9. 키 값 없이 환경 상태를 확인하고 실제 Gemini 검증을 별도로 실행하는 진단 도구를 추가했습니다.

이 항목은 코드 구현 범위이며 실제 MySQL·Gemini 연동 성공을 의미하지 않도록 구분했습니다.

현재 5주차 공개 응답 필드와 기존 Mock 요청 형식은 유지했습니다.

## 5. 서버 정답 조회 및 클라이언트 입력 조작 방지

기존 `Practice` ORM 모델의 ID가 `practices.practice_id`에 대응함을 확인했습니다.
`Content`, `Course`와 조인하고 콘텐츠와 과정 모두 공개된 실습만 평가 대상으로 조회하도록 구현했습니다.
과제 제목·지시문·모범 수식·기대 결과·결과 유형·허용 오차·필수 함수는 서버 자료에서 가져오도록 했습니다.

실제 요청에 클라이언트가 추가한 `expected_answer`, `task_instruction`, `evaluation_criteria`, 점수 등은 무시하도록 구현했습니다.
정답이나 필수 평가 정보가 없으면 모델 호출 전에 보류하도록 구현했습니다.
없는 실습·비공개 실습은 404, 잘못된 입력은 422, DB 의존성·조회 장애는 503으로 처리하도록 구현했습니다.

기존 팀원 DB 모델·관리자 저장 코드를 재사용했으며 해당 파일을 임의로 수정하지 않았습니다.
실제 ORM 조회는 SQLAlchemy가 설치되지 않아 이번 환경에서 검증하지 못했습니다.

## 6. 루브릭 기반 평가 및 할루시네이션 방지 개선

수식 평가에서는 비교 함수 25점, 인수 개수 15점, 인수별 구조 합계 60점으로 서버 점수를 구성했습니다.
100점·1~99점·0점을 각각 정답·부분 정답·오답으로 구분했습니다.
결과값은 NUMBER에서 Decimal과 허용 오차, TEXT에서 문자열 비교를 사용하도록 구현했습니다.

DB의 필수 함수가 선택 필드라는 점을 확인하고 빈 값 자체를 오류로 보지 않도록 개선했습니다.
지시문에서 탐지 가능한 함수 사용 요구와 저장 기준이 충돌하면 보류하도록 구현했습니다.
자연어 지시 전체를 정확하게 해석할 수 있다고 주장하지 않았으며 명시적 루브릭 관리가 후속 과제임을 정리했습니다.

Gemini/OpenAI의 내부 응답에는 항목별 근거 확인 정보를 요구하도록 구현했습니다.
모델 점수·판정·수정 답안·근거가 서버 결과와 다르면 보류하도록 구현했습니다.
학습자에게 표시하는 설명은 검증된 서버 근거로 구성하여 모델이 생성한 임의의 실행·계산 주장을 그대로 보여주지 않도록 했습니다.
Gemini 지시와 학습자 데이터를 분리하고 호출 시간 제한을 설정했습니다.

수식 비교는 제한된 구문과 구조를 대상으로 구현했습니다.
Excel 실행, 워크북 데이터 검증, 모든 다른 풀이의 의미 동등성 판정은 구현하지 않았습니다.
이번 점수를 일반적인 Excel 정답률이나 실제 Gemini 정확도 통계로 해석하지 않도록 명시했습니다.

## 7. Gemini API와 Mock 모드 구현 및 검증 상태

기존 Mock의 고정 예시 점수와 요청 JSON을 유지하고 실제 평가와 구분했습니다.
Mock이 클라이언트 기대 답안을 사용하는 시연 기능임을 문서화했습니다.
실제 API 장애 시 Mock으로 자동 대체하는 동작은 추가하지 않았습니다.

설치된 Gemini SDK의 설정 필드 존재와 대체 SDK 응답을 이용한 요청·응답 검증은 확인했습니다.
환경 변수에서 Gemini 키의 존재 여부만 확인했으며 비밀값은 출력하지 않았습니다.
프로젝트 루트·backend·ai-search에 `.env`가 없었고 환경에도 키가 없어 실제 Gemini 호출은 수행하지 못했습니다.
명시적인 MySQL 연결 정보도 없어 실제 MySQL 연결 성공으로 판단하지 않았습니다.

## 10. 남아 있는 문제와 다음 주 계획

현재 가상환경은 Python 3.15.1이며 SQLAlchemy·PyMySQL·python-dotenv가 설치되지 않았음을 확인했습니다.
설치를 시도했으나 패키지 조회·다운로드에 실패하여 SQLite ORM 통합 검증을 완료하지 못했습니다.
다음에는 팀과 Python·의존성 환경을 맞추고 설치 가능한 환경에서 건너뜀 없이 재검증할 계획으로 정리했습니다.

실제 MySQL 과제와 Gemini 키·모델 접근 권한을 설정한 뒤 실제 API를 확인해야 한다고 정리했습니다.
현지민님께는 공개 실습 ID 제공 방식, 데이터 검수, 인증·호출 제한·이력 저장·정답 공개 정책을 협의할 사항으로 전달하도록 정리했습니다.

사용자 페이지 연결은 이번 범위에서 구현하지 않았습니다.

다른 유효한 수식 풀이와 자연어 제약 판정의 한계가 남아 있어, 다음 주에 평가 세트를 확장하고

현재 작업본에서 `git status`와 `git remote -v`를 실행했으나 Git 저장소가 아니라는 오류를 확인했습니다.
지정된 저장소에 `git ls-remote --heads`로 접속했지만 GitHub 443 포트 연결 실패가 발생했습니다.
따라서 원격 저장소 접근과 기존 브랜치 여부·기준 이력을 확인하지 못했습니다.
네트워크 연결 단계에서 실패했으므로 인증·쓰기 권한의 성공 여부도 판단하지 않았습니다.

기준 이력 없이 팀원 변경을 덮어쓰지 않도록 임의로 빈 저장소를 초기화하거나 main을 수정하지 않았습니다.
커밋·push는 실행하지 못했고 업로드된 파일·커밋 해시·생성된 원격 브랜치는 없습니다.
`feature/week5-ai-feedback`은 지정된 업로드 대상이며 실제 생성·업로드했다고 표시하지 않았습니다.

원본 저장소와 Git 환경이 확인되면 최신 원격 변경을 확인하고 기존 개인 브랜치를 우선 사용해야 한다고 정리했습니다.
그 후 차이를 검토한 AI 담당 파일·문서만 명시적으로 스테이징하고 커밋·일반 push해야 한다고 정리했습니다.
`.env`, 비밀키, 비밀번호, 가상환경, 캐시를 포함하지 않고 팀원 변경을 덮어쓰거나 force push하지 않도록 했습니다.
권한 문제를 우회하거나 main으로 push·merge하지 않았습니다.

## 11. AI 도구(Codex) 사용 내역

Codex를 활용하여 기존 AI 코드·DB 모델·API 구조를 분석하고 개선 계획을 수립했습니다.
서버 조회 경계, 구조 루브릭, 제공자 근거 검증, 독립 데모, 회귀 테스트 초안을 구현하는 데 활용했습니다.
터미널에서 실제 테스트와 환경 진단을 실행하고 출력된 결과를 근거로 통과·건너뜀·미검증을 구분했습니다.
팀원용 연동 안내와 개인 활동 보고서 작성에도 활용했습니다.

Codex의 분석·생성 결과만으로 실제 DB·Gemini 연결 성공이나 평가 정확도를 확정하지 않았습니다.
학교 과제 제출 및 팀 연동 전에 담당자가 문서와 브라우저 동작, 미검증 항목을 직접 확인하도록 정리했습니다.
